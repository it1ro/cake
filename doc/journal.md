## 2026-09-20 — Процессор Go, дерево, тесты

### Что сделано
- `internal/processor` — интерфейс `Processor`, реестр, `Language()`,
  фолбэк `passthrough`.
- `internal/processor/golang` — strip комментариев через `go/printer`,
  сохранение build-констрейнтов и `//go:*` директив, флаг `KeepDoc`.
- `walker.Tree` — ASCII-дерево с `├──` / `└──`, совместимое с `tree(1)`.
- `cmd.clean` — новая команда CLI.
- `pipeline` — режим `ModeDump` / `ModeClean`, прогон через процессор.
- `render/xml` — переключён на `walker.Tree`, эскейпинг `]]>`.
- Тесты: `golang_test.go`, `walker_test.go`, `xml_test.go`.
- Makefile с типовыми целями (build/test/lint/cover/release-snapshot).
- `cmd/cake/main.go` — ldflags-переменные версии.

### Решения
- **`processor.Language` — единая точка правды.** Дублирование с
  `walker` убрано; walker теперь импортирует processor (циклов нет,
  потому что processor не зависит от walker).
- **Регистрация процессоров через `init()` + blank import.** В
  `main.go` явный `_ ".../processor/golang"` — линтер не удалит,
  реестр заполнен к моменту `Execute()`.
- **`f.Comments` не оставляем `nil`.** Если `nil`, `go/printer`
  переключается в `useNodeComments` и печатает комментарии из
  `.Doc`-полей AST, обходя фильтр. Заводим пустой срез явно.
- **Malformed-файл → исходник без ошибки.** Пайплайн не должен
  падать из-за одного битого файла (например, под чужой GOOS).
- **Тесты — `wantContains` / `wantNotContains`, а не golden.**
  `go/printer` может сдвинуть пустые строки; golden-файл будет
  ложно падать на незначительных изменениях формата.
- **Tabwidth=8 в printer.** Как в `gofmt`; отступы всё равно табами
  (`printer.TabIndent`), значение влияет только на выравнивание.

### Открытые вопросы
- Как быть с файлами под чужой `//go:build`? Сейчас — «включать
  всё, помечать в метаданных». Возможно, стоит уважать
  `runtime.GOOS/GOARCH` флагом.
- `//line` директивы: сохраняем, но не факт что нужно — они ломают
  нумерацию строк в выводе. Понаблюдать.
- Оценка токенов — по-прежнему нули в `<context tokens="0">`.
  Ждёт v0.2.

### Решения
- **Не используем `sabhiram/go-gitignore`.** Не поддерживает
  вложенные `.gitignore` и dir-only правила. Свой парсер — 250 строк,

- **Не используем regexp.** Для дерева из 50k путей и сотен правил

- **Не поддерживаем `[...]`.** Редко встречается в .gitignore,
  добавлять сейчас — преждевременно.
- **Загрузка .gitignore до проверки самой директории.** Соответствует
  семантике git.

  все случаи, переписать на канонический матчер с мемоизацией (i, j).
- Читать ли `.git/info/exclude`? Пока нет.
- Поведение с симлинками на директории — сейчас WalkDir не заходит,
  значит и .gitignore там не читается. Ок.

## 2026-09-20 — Токены, бюджет, форматы, clipboard

### Что сделано
- `internal/tokens` — эвристика `len/4`. `<context tokens="...">`
  перестал быть нулём.
- `--budget N` — жадный фильтр: файлы, не влезающие в лимит,
  пропускаются; порядок сохраняется. В выводе появляется
  `dropped="N"`.
- `internal/render/render.go` — диспетчер `Render(ctx, format, w)`,
  `Format` — строковый тип, `Parse` для CLI-флага.
- `internal/render/markdown.go` — заголовки + code-блоки,
  экранирование ``` внутри содержимого.
- `internal/render/plain.go` — для отладки и диффов.
- `internal/clipboard` — OSC 52 через `/dev/tty` (Unix) и
  `CONOUT$` (Windows). Плюс `Copy(w, data)` для тестов.
- `--clipboard` в `dump` и `clean`: tee-вывод в буфер, затем
  OSC 52 в терминал.
- Тесты: `tokens_test`, `clipboard_test`, `render_test`,
  `markdown_test`, `pipeline_test` (бюджет — интеграционный).

### Решения
- **`tokens.Estimate` — len/4, округление вверх.** Для кода и
  латиницы ошибка в пределах 10–15%, для CJK занижает — но
  v0.1 и не обещает точность. tiktoken — v0.2.
- **Бюджет — жадный фильтр, не «стоп на первом». ** В
  отсортированном по пути списке крупный `a.go` может быть
  пропущен, а мелкий `z.go` — пройти. Это лучше, чем
  обрезать всё после первого не влезшего.
- **OSC 52 пишем в `/dev/tty`, а не в stdout.** При
  `cake dump > out.xml` escape-последовательность попала бы
  в сам файл. `/dev/tty` — только терминал.
- **Формат в pipeline — тип `render.Format`, не строка.**
  Zero value = "" трактуется как XML — чтобы `Options{}` не
  падал и не печатал мусор.
- **Копирование в clipboard = tee в bytes.Buffer.** Платим
  памятью за полный дубль вывода, но только под флагом.
  Стриминг в остальных случаях сохранён.
- **Fence в markdown экранируем `‛‛‛` (U+201B).** Markdown-
  парсеры её не трогают; для LLM разница несущественна,
  а структура блока сохраняется.
- **`dropped` — атрибут только при > 0.** Чистый вывод в
  типичном случае; тест `TestXML_AllAttributesQuoted`
  продолжает проходить.

### Открытые вопросы
- Оценка токенов на бинарных файлах — сейчас и они
  оцениваются. Walker отсекает бинарь, но процессор может
  вернуть не-UTF-8. Пока ок: эвристика len/4 работает на

- `--budget` и `--max-size` дублируют друг друга по духу.

## 2026-09-20 — pipeline refactor, TUI pick

### Что сделано
- `pipeline.Plan / Run / RunWith` — разделил обход ФС и рендер.
  `Run` остался как Plan+RunWith для CLI. Новый `RunWith` принимает
  готовый список файлов — это точка входа TUI.
- `tokens.EstimateSize(n int64)` — оценка по размеру, чтобы TUI
  мог считать токены, не читая содержимое.
- `internal/tui` — модель bubbletea: список, курсор, выбор,
  fuzzy-фильтр, live-токены, переключение Mode/Format.
- `cmd/pick` — команда, открывает TUI и вызывает `RunWith`
  по подтверждению. `--format`, `--output`, `--budget`,
  `--clipboard`, `--keep-doc` прокинуты.
- `Makefile: build-matrix` — компиляция под все GOOS без записи
  бинарей. Ловит рассинхрон build-тегов (ср. инцидент с
  `tty_unix.go`, где `//go:build windows` был по ошибке).
- Тесты `tui_test.go` — 10 кейсов: toggle, cursor, select all,
  dir toggle, filter, mode/format cycle, confirmed, порядок,
  токены.

### Решения
- **Развилка A/B закрыта в пользу B.** `RunWith(opts, files)`
  вместо `Options.Files`. Явное «что выводить» отделено от
  «как выводить»; walker не вызывается дважды; TUI не
  дублирует обход. Соответствует `architecture.md`:
  «TUI-режим отличается только источником списка файлов».
- **`Run(opts)` сохранён как convenience.** `cli/dump.go` и
  `cli/clean.go` не переписывались — они и так корректны.
  Разделение затрагивает только новые точки входа.
- **TUI не читает содержимое файлов.** Только метаданные
  (Path, Size). Токены в футере — оценка по размеру
  (`EstimateSize`), не по контенту. В clean-режиме это
  оценка сверху: комментарии будут удалены, содержимое
  уменьшится. На v0.1 приемлемо.
- **`SelectedFiles` возвращает в порядке `all`, а не в
  порядке выбора.** `all` уже отсортирован `walker.Walk` —
  детерминизм вывода сохраняется (важно для diff).
- **TUI не импортирует walker.** Только `pipeline`, `render`,
  `tokens`, `types`. Если бы импортировал — пришлось бы
  дублировать `walker.Options`. Так — одна точка правды.
- **Порядок выбора восстанавливается по `all` в
  `SelectedFiles`.** Это ловит `TestSelectedFiles_PreservesOrder`:
  даже если пользователь выбрал в обратном порядке, вывод
  детерминирован.
- **`d` = toggle директории текущего файла.** Не по курсору
  на «дереве», а семантически — «всё в той же папке».
  Достаточно для 90% случаев; полноценное дерево с
  раскрывающимися узлами отложено.
- **`inFilter` — отдельное состояние, не «TUI в режиме ввода».**
  Вне фильтра печатаемые символы — команды; внутри —
  буквы фильтра. Классическая модальность vim-style, знакома
  пользователям `fzf`/`telescope`.

### Открытые вопросы
- **Скроллинг списка.** Сейчас окно сдвигается по курсору,
  но без индикаторов «есть ещё выше/ниже». На длинных
  списках (10k+) не хватает. Возможно — счётчик `start-end/total`
  в статусе.
- **Ширина терминала.** Длинные пути обрезаются? Сейчас нет —
  строка выходит за границу, терминал сам переносит. Может
  резать по `m.width` с `…` в середине.
- **`esc` в нормальном режиме.** Сейчас — no-op. Стандартно
  в TUI это либо «отмена», либо «назад». У нас некуда
  возвращаться; оставить no-op или сделать quit?
- **Symlinks.** Walk не заходит в симлинки на директории. В TUI
  это выглядит как «файла нет», хотя он есть в ФС. Не
  всплывало в тестах, понаблюдать.

## 2026-09-20 — tree-режим в TUI pick

### Что сделано
- `internal/tui/tree.go` — дерево из плоского списка FileEntry:
  `Node`, `buildTree`, `flatten`, `markMatches`, `selectState`,
  `fileDescendants`. Директории сортируются вперёд файлов, внутри
  групп — по имени (совместимо с `walker.Tree` и `tree(1)`).
- `internal/tui/model.go` — переключатель `treeMode`; хоткей `t`;
  навигация `←`/`→` + `h`/`l` (collapse/expand, переход к родителю
  на свёрнутой директории); `space` на директории — toggle всего
  поддерева; `d` теперь mode-aware.
- `internal/tui/view.go` — `renderTreeLine` с маркерами `[x]/[-]/[ ]`,
  `▾/▸` для раскрытия, `dirStyle` для директорий, `partialStyle`
  для частичного выбора. Статус-строка показывает `list|tree`.
- `internal/tui/tui_test.go` — 5 новых тестов: toggle tree/list,
  collapse/expand, select dir, partial select, фильтр сохраняет
  родителей. Плюс `TestViewHeightStable` и
  `TestTreeModePreservesCursor` — фиксируют два инварианта, которые
  легко сломать рефакторингом.
- Тесты `TestTreeCollapse`, `TestTreeSelectDir`, `TestTreePartialSelect`
  изначально падали — `t` сохраняет курсор на текущем файле, а не
  сбрасывает в начало (см. решения). Фикс — `g` после `t` в тестах,
  не в коде.

### Решения
- **Дерево — отдельная модель данных, не второй обход ФС.**
  `buildTree(all)` строится из того же `[]FileEntry`, что приходит
  от `pipeline.Plan`. Это третья (после плоского списка и CLI)
  проекция одного источника — обхода walker'а.
- **`t` сохраняет курсор на текущем файле.** В flat cursor=0, `t`
  переводит на тот же файл в дереве — курсор «прилипает» к пути,
  не к индексу. Обратно — тоже. Зафиксировано
  `TestTreeModePreservesCursor`; тесты `TestTree*` падали именно
  на этом — предполагали сброс, а поведение сознательное.
- **Фильтр в дереве — подстрочный (contains), не fuzzy.** Fuzzy
  в flat переупорядочивает результаты по релевантности; в дереве
  это ломало бы структуру (родитель мог уехать ниже ребёнка).
  В tree остаёмся на строгом «скрыть всё, что не подходит», а
  родители совпадений сохраняются, чтобы ветки были видны.
- **`forceExpand` при непустом фильтре.** Если ветка свёрнута, а
  внутри есть совпадение — при фильтре раскрываем принудительно.
  Иначе совпадение было бы «найдено, но не показано».
- **`space` на директории — toggle всего поддерева, не expand.**
  Expand — на `→`/`l`. Так совпадает с `telescope`/`nvim-tree`,
  где `space` — «выбрать всё в узле».
- **Маркер директории `[-]` при частичном выборе.** Пользователь
  видит, что под директорией что-то выбрано, не разворачивая её.
  Считается через `selectState` (число выбранных файлов / всего).
- **`d` в tree-режиме работает по семантике узла.** Курсор на
  директории — toggle этой директории; на файле — toggle его
  родителя. В flat — toggle родительской директории файла. Один
  хоткей, разные контексты — привычно для тех, кто работал в
  `ranger`/`lf`.
- **Родительские ссылки в `Node`.** `Parent *Node` — чтобы `←`
  на свёрнутой директории шёл к родителю, а не был no-op. Плюс
  используется в `currentDirPrefix` для `d`.
- **`viewChrome`/`filterLine` вынесены в константы.** После
  добавления tree-режима `View` стал на 1 строку длиннее (статус
  показывает `view`), а магическая `7` в `renderList` — уже
  разъезжалась. Теперь одна точка правды; ловится
  `TestViewHeightStable`.

### Открытые вопросы
- **`a`/`A` в tree работают по всему `all`, а не по видимому.**
  Осознанно: «выбрать весь проект» — частая операция, `space`
  на корне неудобен. Но если пользователь свернул `cmd/` и жмёт
  `a`, файлы под `cmd/` тоже выбираются — надо ли это? Пока да,
  понаблюдать.
- **Persistence раскрытия.** Сейчас всё раскрыто при первом `t`;
  на 50k-файловом репо это шквал. Стоит ли стартовать свёрнуто
  на глубине > 2 или хранить состояние в `~/.cache/cake/`?
- **Курсор после `esc` в фильтре.** Сбрасывается на первый
  элемент, потому что список изменился. Иногда хочется остаться
  на том же файле, если он остался видим. Понизить до косметики
  или пофиксить?
- **Стили и вложенные ANSI.** `cursorStyle` (Reverse) поверх
  `dirStyle` (Bold) — проверял в iTerm2 и WezTerm, ок. На
  терминалах без truecolor может выглядеть грязно, но не
  ломается.

- Новое распределение target:
  - `--output` — файл
  - `--clipboard` — только буфер (и summary в stderr)
  - `--output + --clipboard` — файл и буфер
  - без флагов — stdout
- Описание `--clipboard` в `dump`/`clean`/`pick` поправлено:
  «скопировать в буфер; вместо stdout», а не «дополнительно».
- `TestRunWith_Clipboard_NoStdout` — перехватывает os.Stdout
  через пайп и проверяет, что при `--clipboard` туда не ушло
  ни байта.

### Решения
- **`--clipboard` = «в буфер, а не в терминал».** Пользователь
  с `cake .` ожидает «взял → вставил». XML на экране при этом
  не нужен и мешает — приходится прокручивать, чтобы увидеть
  summary. Раньше было «и туда, и туда», что разумно для `-o`
  (сохранить в файл и скопировать), но не для голого
  `--clipboard`.
- **`--output` остаётся ортогональным.** Файл — самостоятельный
  назначение; сочетание с `--clipboard` даёт оба. Не смешиваем
  «сохранить» и «скопировать».
- **Summary остался в stderr.** Он — единственный видимый
  признак успеха, когда stdout молчит. Именно ради этого
  случая он и был вынесен в stderr, а не в stdout.
- **Тест через `os.Pipe`, не через рефакторинг.** Вынос
  выбора `target` в отдельную функцию ради тестируемости
  добавил бы API ради теста. Пайп — три строки и прямая
  проверка инварианта.
- **Горутина в тесте — вынужденно.** `os.Pipe` блокируется
  на запись, если никто не читает. `io.Copy` в главной
  горутине разблокирует писателя. `done`-канал гарантирует,
  что мы не читаем после закрытия.

### Открытые вопросы
- **Что если пользователь хотел именно «скопировать и
  посмотреть»?** Раньше мог, теперь нет. Обходные пути:
  `--output -` (если добавим поддержку «-» как stdout) или
  `cake dump . > /tmp/x && cake dump . --clipboard`. Пока
  считаем редкостью.
- **`TestRunWith_Clipboard_NoStdout` мутирует `os.Stdout`.**
  Если в pipeline когда-нибудь появятся параллельные тесты —
  они поломаются. `t.Setenv` для stdout нет; на будущее —
  не забыть пометить тест `//nolint:paralleltest` или
  переделать на инъекцию writer'а.
- **`Summary` пишет про `buf.Len()`, а не про размер того, что
  реально попало в буфер терминала.** OSC 52 имеет свои лимиты
  (например, xterm режет на 100 KB). Мы об этом не узнаем.
  Понаблюдать за поведением на больших репозиториях.

## 2026-09-20 — бенчмарк на kubernetes/kubernetes

### Результаты
- `cake dump .` на k8s (`--depth=1`, без `_output/`):
  - wall time: **2.6 сек** (критерий — < 5 сек)
  - files: **24 924**
  - tokens: **47.1M** (эвристика len/4)
  - размер XML: **194 MB**
- Все пять бинарей: 4.3–4.7 MB stripped (критерий — < 15 MB).
- `make cover`: 78% total. По ключевым пакетам — 80–100%
  (walker 82%, processor/golang 87%, render 94.5%, tokens 100%,
  tui 81.6%).

### Решения
- **`isBinary` оставляем как есть.** 25k syscall'ов на открытие
  файла оказались дешёвыми на SSD: из 2.6 сек на них уходит
  незначительная часть. Оптимизация через кэш расширений —
  преждевременна; если понадобится, v0.2.
- **`--budget` — не «приятное дополнение», а обязательный
  инструмент.** 47M токенов из k8s не влезут ни в один контекст
  (Claude 200k, GPT-4 128k). Пользователь обязан либо
  фильтровать (`-i`), либо обрезать (`--budget`). README должен
  это явно объяснять в quick start.
- **Кросс-сборка работает.** `make build-all` даёт пять артефактов
  без ошибок, включая windows/amd64 (`tty_windows.go` с `CONOUT$`
  компилируется).
- **Покрытие зафиксировано.** 78% total — выше критерия 60%.
  Нули в `cli` и `processor` — обвязка, там тесты не нужны.

### Открытые вопросы
- **`clean` на k8s не гоняли.** Стоит прогнать отдельно:
  `cake clean . -i "**/*.go" --budget 50000 -o /tmp/x.xml`.
  Ожидание: 5 сек, ~600 KB, валидный XML.
- **XLS vs markdown на 200 MB.** Markdown-рендер в 1.5–2 раза
  больше XML (заголовки, backticks). Не критично, но проверить
  стоит перед README.
- **`--budget` в summary.** `dropped="N"` уже показывается, но
  в stderr-summary от clipboard — тоже (в `stats` есть `dropped N`).
  Хорошо.
