# ADR 001: Лимит контекста и реакция на переполнение

- **Статус:** Accepted (rev. 2)
- **Дата:** 2026-09-20
- **Контекст-релиз:** v0.2
- **Связано:** `01-requirements.md`, `02-architecture.md`, `04-roadmap.md`,
  `reviews/001-adr-context-limit/review-results.md`

> **Изменения по ревью.** Реализация следует
> `reviews/001-adr-context-limit/review-results.md`. Где этот ADR
> расходится с ним, приоритет у `review-results.md`. Ключевые поправки:
>
> - Убран `suggest` и интерактив в `dump`/`clean`. Дефолт `--on-overflow`
>   не зависит от TTY: `fail` при заданном лимите, `drop` — явный флаг.
> - Код переполнения — `3` (`2` занят usage-ошибками и совпадает с кодом
>   make при падении рецепта).
> - Семантика флагов: эффективный потолок = `min(budget, limit − reserve)`.
>   `--budget` остаётся жёстким фильтром как раньше.
> - Проверка в dump — сразу после `Plan`, без чтения файлов. В clean —
>   после процессоров, до render. Одна авторитетная точка — `pipeline.Check`.
> - Отчёт: `report.Report` — структура данных, текст и JSON — представления
>   над ней. Веса в токенах, `schema: 1`.
> - Оценка = `content_tokens + overhead_tokens`, где `overhead` считается
>   прогоном настоящего рендера с пустым содержимым.
> - `cake.toml`: `version = 1`, профили с неявным наследованием,
>   strict-разбор через `pelletier/go-toml/v2`. Ключ `mode` удалён.
> - `reserve` — число или процент; дефолт `clamp(limit/10, 1000, 20000)`.
>   Не наследуется профилем, переопределившим `context-limit`.
> - Пропущенные файлы остаются в `<tree>` схлопнутыми директориями
>   (`types.Context.Omitted`), а не растворяются в `dropped="N"`.
> - TUI: индикатор лимита в существующей статусной строке, без блокировки
>   `enter` и без авто-обрезки.
> - Пример отчёта с `vendor/` неактуален: `walker.Walk` отсекает `vendor/`
>   безусловно, `--exclude 'vendor/**'` был бы нулевой мерой.

## Контекст
## Контекст

`cake` готовит контекст для LLM, но у каждой модели есть жёсткий
лимит входного окна: Claude ~200k, GPT-4 ~128k, локальные модели —
от 4k до 32k. Превышение — не «предупреждение», а отказ: либо API
вернёт ошибку, либо пользователь вставит в чат половину дампа и не
заметит, что вторая половина потерялась.

Сегодня единственный инструмент контроля — `--budget N`:

```go
if opts.Budget > 0 {
    kept := processed[:0]
    for _, f := range processed {
        t := tokens.Estimate(f.Content)
        if total+t > opts.Budget {
            dropped++
            continue
        }
        total += t
        kept = append(kept, f)
    }
    processed = kept
}
```

Это **жадный фильтр**: файлы сверх лимита молча выкидываются, в XML
добавляется `dropped="N"`. Проблемы:

1. **Пользователь ставит `--budget 200000` наугад.** Откуда взяться
   правильному числу, если лимит модели не записан нигде в проекте?
2. **Обрезка молчаливая.** `dropped="47"` — это одна цифра в одном
   атрибуте. За ней может стоять `vendor/`, `testdata/` и половина
   `internal/`. Пользователь вставит дамп в LLM и не поймёт, почему
   модель «не видит» файл.
3. **Нет диалога.** `cake` знает всё, что нужно для совета («вот тут
   63% веса»), но советовать не умеет — только рубить.

Из требований (`01-requirements.md`) это не закрыто: там про
`--budget` вообще нет, а про критерий готовности сказано только
«бенчмарк на kubernetes/kubernetes без падений». Пора зафиксировать
поведение явно.

## Решение

Ввести **декларацию лимита** (`--context-limit` + `cake.toml`) и
**реакцию на переполнение** (`--on-overflow` + агрегированный отчёт).
`--budget` остаётся как есть — это «жёсткий потолок», новая сущность
— «цель, которую мы хотим уложить».

### 1. Две независимые величины

| Флаг | Семантика | Поведение при превышении |
|---|---|---|
| `--budget N` | «сколько я готов отдать» (потолок) | молча обрезать, `dropped="N"` |
| `--context-limit N` | «сколько влезает у модели» (цель) | по `--on-overflow` |

Могут задаваться одновременно. `--budget` работает как сейчас —
финальная обрезка. `--context-limit` — как вход в диагностику.

### 2. Источники лимита и приоритет

```
--context-limit <CLI>  >  ./cake.toml  >  ~/.config/cake/config.toml  >  нет лимита
```

Локальный `cake.toml` — в корне проекта, не в XDG-конфиге: лимит и
исключения часто «на репо» (один проект — одна рабочая модель, один
набор «шумных» директорий). Глобальный — для личных настроек,
переносимых между проектами. Профили — чтобы один репо обслуживал
несколько сценариев (быстрая модель, большая модель, CI).

```toml
# cake.toml

[default]
context-limit = 200_000   # сколько влезает у модели
reserve       = 20_000    # оставить на system prompt + ответ
format        = "xml"
mode          = "dump"
on-overflow   = "suggest"

[profiles.local]
context-limit = 32_000
format        = "markdown"

[profiles.cheap]
context-limit = 128_000
exclude = ["**/*_test.go", "vendor/**", "testdata/**"]

[profiles.ci]
on-overflow = "fail"
```

Использование: `cake dump . --profile cheap`. Без `--profile` берётся
`[default]`. CLI-флаги поверх конфига — побеждают.

### 3. Pre-flight и post-flight

Две проверки, с разной точностью и стоимостью:

**Pre-flight** — до чтения содержимого, по `Size` из `walker.Walk`:

```go
total := int64(0)
for _, e := range entries { total += e.Size }
est := tokens.EstimateSize(total)
if est > opts.ContextLimit - opts.Reserve {
    return reportOverflow(entries, est, opts)
}
```

Быстро (только метаданные), даёт оценку **сверху**: в `clean`-режиме
комментарии будут удалены, файлы уменьшатся на 10–30%. Ошибка —
в безопасную сторону: реже пропустим реальное переполнение.

**Post-flight** — после процессоров, по точному `Tokens`:

```go
if total > opts.ContextLimit - opts.Reserve {
    return reportOverflow(processed, total, opts)
}
```

Дороже (уже прочитали все файлы), но точнее. Включается только
если pre-flight прошёл, а `--context-limit` задан.

### 4. Отчёт при переполнении

Ключевое: не «вот тебе список из 500 файлов», а **агрегация**.
Пользователь хочет знать, где вес, а не какие имена.

```
⚠ не влезаем: ~247k tok при лимите 200k (резерв 20k)

Что даёт больше всего:
  vendor/           124 MB   31.0M tok   63%
  testdata/          42 MB   10.5M tok   21%
  internal/tui/     1.2 MB    0.3M tok    0.6%

Файлов по расширениям:
  .go    1823 файла   38.1M tok
  .md     412 файлов   8.4M tok
  .json    88 файлов   2.1M tok

Возможные меры:
  • --exclude 'vendor/**' --exclude 'testdata/**'  → ~178k tok (влезает)
  • --include '**/*.go'                            → ~39M tok
  • --mode clean  (снять комментарии в Go)         → оценка сверху -15%
  • cake pick .   (выбрать вручную)
  • --profile cheap  (128k + исключения из cake.toml)
```

Каждая мера — **с оценкой эффекта**. Это сближает `cake` с `du`/`ncdu`:
«вот где вес, решай». Отчёт идёт в stderr — stdout остаётся чистым,
потому что никакого контента ещё нет.

Источники мер:
- **excludes**: топ-3 директории по суммарному весу, которых нет в
  текущих `--exclude`.
- **includes**: топ-расширения по весу — как альтернатива «оставить
  только нужное».
- **clean**: применяется, если `Mode == dump` и есть `.go`-файлы.
- **pick**: подсказка без оценки.
- **profile**: если в `cake.toml` есть профиль, укладывающийся в лимит
  по pre-flight-оценке.

### 5. Реакция: `--on-overflow`

Три режима, дефолт зависит от TTY:

| Значение | Когда дефолт | Поведение |
|---|---|---|
| `suggest` | TTY | показать отчёт, спросить действие |
| `drop` | pipe / CI | молча обрезать до `limit - reserve` (текущее поведение `--budget`) |
| `fail` | — | отчёт + `exit 2`, вывода нет |

Интерактивный `suggest`:

```
[o]btrim  [e]xclude  [p]ick  [a]bort >
```

- `o` — прогнать с `--budget = limit - reserve` (жадный фильтр).
- `e` — предложить первый набор excludes из отчёта, переспросить.
- `p` — запустить TUI pick с уже проставленными исключениями.
- `a` — выход с `exit 2`.

`suggest` требует TTY. Если stdin не терминал — принудительно
деградирует до `drop` (с предупреждением в stderr). `--on-overflow`
можно зафиксировать в `cake.toml`, чтобы CI-профиль не зависел от
окружения.

### 6. Интеграция с TUI (`cake pick`)

У `pick` уже есть live-оценка токенов в футере. Логично добавить
индикатор лимита:

```
[ dump ] · xml · 14/61 · 25/61 sel · ~180k / 200k
                                       ^^^^^^^^^^^^^^
                                       зелёный → жёлтый (90%) → красный
```

При превышении `enter` блокируется, показывается `press o to
obtrim, esc to continue`. Само действие `o` — то же, что и в CLI:
применить `--budget = limit - reserve`.

## Обоснование

### Почему не переименовать `--budget` в `--context-limit`

Это разные сущности. Лимит модели — свойство среды, не решение
пользователя. Пользователь может хотеть отдать меньше лимита
(например, экономить деньги на API) или больше (знает, что модель
справится с переполнением через truncation на стороне API — редко,
но бывает). Слить их — потерять выразительность.

Плюс `--budget` уже есть и описан в README; ломать совместимость
без нужды — плохо.

### Почему `cake.toml`, а не `.cake.toml`

Скрытые файлы в корне репо — это файлы, которые «не хочется
показывать в `ls`». `cake.toml` не такой: он часть проекта, как
`Makefile` или `go.mod`. Скрывать его — значит поощрять
невидимую конфигурацию.

### Почему профили, а не один лимит

У одного пользователя — минимум три контекста:
- локальная модель на ноутбуке (32k),
- рабочая Claude через API (200k),
- CI, где `cake` собирает снапшот для артефакта (128k).

Один лимит вынуждает либо редактировать `cake.toml` перед каждым
запуском, либо держать три файла. Профили — стандартный паттерн
(`goreleaser`, `docker-compose`), читается без объяснений.

### Почему pre-flight агрегированный, а не «список крупных файлов»

Список крупных файлов — шум. Пользователь не удалит `vendor/k8s.io/api/core/v1/types.go` из проекта; он исключит `vendor/`.
Агрегация по директориям и расширениям отвечает на вопрос «что
тянет вес», а не «какие именно файлы». Список файлов — вторичен,
и он есть в `cake pick`.

### Почему `--on-overflow=drop` по умолчанию в pipe

В `cake dump . -o ctx.xml > /dev/null` пользователь ожидает
детерминированный выход, а не интерактивный вопрос, который
повиснет в скрипте. `drop` — то же поведение, что было у `--budget`
при отсутствии лимита: не сломает существующие пайплайны.

### Почему `reserve` — отдельная величина

Лимит контекста — это **весь** промпт, куда входит:
- system prompt (сотни-тысячи токенов),
- история диалога (если `cake` встраивают в чат),
- собственно ответ модели.

`reserve` — грубая компенсация. Дефолт 10% от лимита — эвристика:
для Claude (200k) → 20k, для локальной (32k) → 3.2k. Пользователь
может задать явно, если знает свой system prompt по цифре.

## Последствия

### Что меняется в коде

- **`internal/config`** — новый пакет. Читает `cake.toml` (local +
  global), мержит с `pipeline.Options`, отдаёт профиль. Зависимость:
  `github.com/BurntSushi/toml` или `pelletier/go-toml/v2`.
- **`internal/pipeline`** — поля `ContextLimit`, `Reserve`,
  `OnOverflow` в `Options`. Pre-flight в `Run` (до `Plan`),
  post-flight в `RunWith` (после бюджетного фильтра).
- **`internal/report`** — новый пакет. Агрегация по директориям и
  расширениям, генерация отчёта. Отдельно от `render`, потому что
  это stderr и другая структура.
- **`internal/cli/*`** — новые флаги `--context-limit`, `--profile`,
  `--on-overflow`, `--reserve`. Чтение `cake.toml` в `PersistentPreRunE`.
- **`internal/tui`** — индикатор лимита в статусной строке,
  блокировка `enter` при переполнении.
- **`cmd/cake/main.go`** — обработка `exit 2` без печати стека.

### Что меняется в UX

- `--context-limit` появляется во всех трёх командах (`dump`, `clean`, `pick`).
- Первый запуск `cake dump .` в репо без `cake.toml` — то же поведение,
  что и раньше (нет лимита → нет проверки).
- `cake dump .` в репо с `cake.toml` — лимит применяется молча в
  pipe-режиме, с предложением мер в TTY.

### Что меняется в документации

- README: новый раздел «Лимит контекста», пример `cake.toml`,
  объяснение `suggest` / `drop` / `fail`.
- `02-architecture.md`: `internal/config`, `internal/report` в схеме.
- `03-stack.md`: TOML-парсер в зависимостях.
- `04-roadmap.md`: пункт «лимит контекста» переезжает из v0.4 в v0.2.

### Что НЕ входит в этот ADR

- **Точная оценка токенов (tiktoken).** Отдельное решение, отдельный
  ADR. Пока — эвристика `len/4` с явным дисклеймером в отчёте.
- **MCP-сервер.** Там лимит будет другой (клиент задаёт), но это
  отдельная интеграция.
- **Плагины / кастомные меры.** Формат отчёта задуман расширяемым,
  но реестр «мер» — преждевременно.
- **Автоматический выбор профиля** по имени модели. Требует
  угадывания, откуда запущен `cake`; оставляем явным.

## Ловушки, которые надо держать в голове

1. **Pre-flight ≠ post-flight.** Walker знает размер на диске,
   процессор — размер после обработки. В `clean` расхождение
   до 30%. Отчёт должен явно писать «оценка сверху».
2. **`--context-limit` без `--budget`.** Ничего не отсекаем
   автоматически — только предупреждаем (в `suggest`) или падаем
   (в `fail`). В `drop` подразумевается неявный
   `--budget = limit - reserve`. Это надо явно задокументировать.
3. **TUI-оценка сейчас — оценка сверху по `Size`.** В `clean`
   переоценка может быть в разы. Лимит в статусе — тоже оценка
   сверху. Смириться на v0.2, чинить с tiktoken.
4. **`os.Pipe` в тестах и `isTTY`.** Определение «TTY vs pipe» —
   через `os.ModeCharDevice`, как в `summary.go`. Тест на дефолт
   `--on-overflow` должен подменять stdout пайпом.
5. **TOML-зависимость.** Сейчас `go.mod` намеренно тощий. TOML-парсер
   — первая «крупная» зависимость после cobra/bubbletea. Альтернатива
   — свой парсер на 200 строк. Скорее всего, `pelletier/go-toml/v2`
   (активно поддерживается, без CGo). Решить при реализации; если
   смущает — вынести отдельным ADR.
6. **`exit 2` vs `exit 1`.** `1` — ошибка (не смогли прочитать файл),
   `2` — «не влезли». Скрипты могут различать. Это контракт, его
   надо задокументировать в `README` и в `Long` у `--on-overflow`.

## Открытые вопросы

1. **`--context-limit` отдельным флагом или переименовать `--budget`?**
   Решено: отдельный. Пересмотреть, если UX окажется перегружен.
2. **Профили — сразу или в v0.3?** Минимум `[default]` в v0.2;
   профили — если не задержит. Не критично для core-value.
3. **Interactive `suggest` — сразу или отчёт+exit 2?** Минимум
   (отчёт + `fail`/`drop`) — в v0.2, интерактив — в v0.3.
   Аргумент: интерактив требует TUI-инфраструктуры, которая уже
   есть (`pick`), но добавляет режим в `dump`/`clean`, где его
   раньше не было.
4. **Pre-flight до или после `Plan`?** Технически — после: `Plan`
   уже даёт `[]FileEntry` с `Size`. «До Plan» невозможно без
   второго обхода. Значит: `Plan` → pre-flight → при переполнении
   развилка → `RunWith`.
5. **`reserve` — процент или абсолют?** Абсолют проще объяснить
   и предсказуемее. Дефолт — `min(20_000, limit/10)`.
6. **Что делать с `--budget` + `--context-limit` + `--on-overflow=drop`?**
   Если `budget > limit - reserve` — предупредить («бюджет больше
   лимита, обрежется по лимиту»). Если меньше — работает `budget`,
   лимит не сработает.

## Что дальше

1. **Реализация минимума (v0.2)** — этот ADR как ТЗ:
   - `internal/config` с одним `[default]` (без профилей).
   - `--context-limit`, `--reserve`, `--on-overflow=drop|fail|suggest`.
   - Pre-flight отчёт с агрегацией по директориям и расширениям.
   - `suggest` без интерактива — печатает меры + `exit 2`.
2. **Интерактив `suggest` и профили (v0.3)** — отдельный ADR,
   если появятся неочевидные решения.
3. **tiktoken (v0.3)** — отдельный ADR. Меняет точность pre-flight
   и post-flight, но не структуру решения.
